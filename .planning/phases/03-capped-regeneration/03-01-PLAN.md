# Plan 03-01: Build Storyboard Attempt State Machine

## Objective

Create a deterministic, append-only controller that enforces the three-candidate cap and preserves the complete storyboard attempt history.

## Requirements Covered

- REGEN-01
- REGEN-02
- REGEN-03
- REGEN-04

## Must Haves

1. An attempt cannot advance until the prior candidate has a recorded QA result.
2. The controller refuses a fourth candidate before any provider call.
3. Candidate states distinguish reserved, generated, passed, failed, manual-review, blocked, and selected.
4. Each attempt records prompt/spec/image/QA paths or hashes and the reason for retry.
5. A three-failure/manual-review outcome is explicitly blocked for Seedance.

## Tasks

### Task 1: Define attempt records and transitions
- Add a focused module beside the Phase 2 QA evaluator.
- Validate allowed transitions and reject skipped QA or illegal state changes.
- Keep history append-only and make the current decision derivable from records.

### Task 2: Add archive and promotion helpers
- Preserve failed candidates in archive paths without overwriting existing artifacts.
- Promote exactly one passing candidate as active.
- Refuse promotion of `fail` or `manual_review` results.

### Task 3: Add deterministic tests
- Test candidate-one-before-candidate-two sequencing.
- Test the hard three-attempt cap.
- Test pass selection, failure archive, third-failure blocking, duplicate attempt prevention, and missing QA prevention.

## Dependencies

- Phase 2 `evaluate_report()` result contract.
- Existing production archive conventions and generation log patterns.

## Verification

- Focused unit tests with temporary production folders.
- Test that no provider callback is invoked when the cap or gate blocks.
- Test append-only history and active-candidate uniqueness.
- Run Python compilation and `git diff --check`.
