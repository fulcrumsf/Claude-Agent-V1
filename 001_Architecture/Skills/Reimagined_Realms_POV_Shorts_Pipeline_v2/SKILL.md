# Reimagined Realms POV Shorts Pipeline — v2 (Seedance 2.0 test)

Vertical (9:16), historical "day in the life" POV videos with no dialogue for the Reimagined Realms channel. This is a **versioned duplicate** of `Reimagined_Realms_POV_Shorts_Pipeline` (v1) — created 2026-08-04 per Tony's instruction to never edit an active pipeline in place for a version-driven architecture change (see `[[feedback_video_pipeline_versioning]]` in Claude's memory). v1 is untouched and still the production-proven path (Seedance 1.5 Pro, single per-shot image, no character/environment sheets). v2 exists to test whether Seedance 2.0's multi-reference-image conditioning fixes the identity-drift problem found in v1's Pyramid Builder I. Deep production (see `Case_Studies/003_Pyramid_Builder_I_Deep_Continuity_Review/` and `Case_Studies/004_Seedance_Storyboard_Character_Consistency_Tutorial/` under Reimagined Realms) — full research trail in [Seedance-Prompting-Guide/SKILL.md](../Seedance-Prompting-Guide/SKILL.md) — the living reference for all Seedance capability/prompting questions, read it before writing or debugging any prompt in this pipeline.

**This is a proof-of-concept, not a locked architecture.** Tony has explicitly flagged multiple open questions that only real test results can answer — see "Known open questions / fallback paths" below before assuming any single approach is final.

**Round 2 update (2026-08-06):** the round-1 "character sheet + environment sheet only, no per-shot image" architecture was tested end-to-end on the Titanic Stoker production and shipped real problems: no per-shot camera lock meant shots drifted from their intended action (a "wipe sweat" beat rendered as an unintended collapse; the dressing beat rendered third-person instead of true POV since the only human reference was the character sheet's own outward-facing framing), and multi-person shots duplicated the same face across every background character since only one character reference existed. Fixed by: (1) storyboard generation now produces one full-resolution, individually-generated, POV-locked 9:16 panel per beat — not a single combined grid — which becomes that shot's `first_frame_url`; (2) character sheets are now per-role (`Main_Character_Sheet.png`, `Background_Worker_Sheet.png`, etc.), referenced in multi-person prompts via ByteDance's own `@Image1`/`@Image2` ordinal-tagging syntax (confirmed live via BytePlus ModelArk docs, see Seedance-Prompting-Guide); (3) `video_generation.py` now accepts an optional `first_frame_url` alongside `reference_image_urls`. See "What's new in v2 vs. v1" below for the full before/after.

**Round 3 update (2026-08-08):** validated end-to-end via two real test productions (Titanic Stoker, then Roman Gladiator) run manually with one-off tool calls before any code changed, per Tony's explicit "prove it before you build it" instruction. Confirmed findings now locked into code: (1) environment sheets must be **one sheet per location, one panel per scene, never merged/reused** — a combined-scene panel silently dropped an entire action beat (a door-push) when two scenes shared a room; (2) environment sheets must be **strictly people-less** (no hands, arms, or crowd figures, even distant/background) — the model kept leaking hands/figures into "empty room reference" panels across several regeneration passes; (3) prop sheets are a new required asset — any asymmetric prop (e.g. a shield) needs explicit **front/back/held-from-POV** panels, not just a "hero" front angle, or the model has nothing correct to render the reverse/carry orientation from (confirmed failure: a shield rendered backwards in 3 scenes because only its decorative front face existed as reference); (4) storyboard panels now explicitly name which labeled sheets/panels they're using via `sheet_labels`, matching the one proven-working reference pattern — **attach the whole sheet image, never crop a panel out of it, and name the specific label in the prompt text**; (5) a new scene-writing checklist (`POV_Style_Guide.md`) must be run on every scene description before it becomes a generation prompt — it catches POV-visibility impossibilities (can't see your own shoulder), ambiguous body position ("looking up" while lying vs. standing), and action-mechanics errors (push vs. pull) that plain pose/camera checks missed. See "What's new in v2 vs. v1" and the Environment Sheet / Prop Sheet / Storyboard sections below for the full detail.

See the original design at `001_Architecture/Superpowers/Specs/2026-08-01-RR-POV-Shorts-Pipeline-Design.md` and the distilled reference conventions at `POV_Style_Guide.md` in this folder (unchanged from v1).

## What's new in v2 vs. v1

| | v1 | v2 |
|---|---|---|
| Video model | Seedance 1.5 Pro via WaveSpeed | Seedance 2.0 (`standard` mode) via kie.ai — WaveSpeed's Seedance 2.0 endpoint doesn't expose the reference-image array, kie.ai's does (confirmed live, see [Seedance-Prompting-Guide](../Seedance-Prompting-Guide/SKILL.md)) |
| Per-shot reference | One first-frame image, generated fresh per shot via GPT-Image-2 | That shot's own POV-locked scene image as `first_frame_url` alone — consistency is already baked in at the image stage (character/prop/environment sheets were used as `input_urls` when the scene image itself was generated), and `first_frame_url` + `reference_image_urls` are mutually exclusive on the live video endpoint (confirmed 2026-08-08) |
| New assets generated | — | Character sheet(s) — one per distinct character, named by role — environment sheet(s) (one per location, one panel per scene), prop sheet (front/back/held-from-POV per recurring prop), storyboard (one individually-generated POV-locked panel per beat, doubles as that shot's `first_frame_url`, explicitly naming which sheet labels it uses) |
| Beat structure | ~5s/scene, 65s floor | Unchanged — same `beat_planning.py`, same 65s floor |
| Video resolution | up to 1080p | 720p max (kie.ai Seedance 2.0 endpoint only offers 480p/720p, no 1080p) |

## Character Sheet (built, now per-role)

`character_sheet_generation.py` — `generate_character_sheet(character_description, output_path, role="the main character", aspect_ratio="1:1", resolution="2K", input_urls=None)`. Generates one 3x3-grid reference image (front/side/back/full-body, expressions, and — because this is POV — dedicated close-up panels on hands/forearms and feet/footwear, since POV shots show those constantly and hands were the primary drift source in the Pyramid Builder review) via GPT-Image-2.

**Generate one sheet per distinct character, not one sheet total.** If a shot has background/supporting characters, each one needs their own sheet — Seedance has no other identity to draw from and will duplicate the same face across everyone in a multi-person shot otherwise (confirmed failure mode: Titanic Stoker shot 9, three stokers, all identical faces, traced to only one character sheet existing). Name the output file for what it is — `Main_Character_Sheet.png`, `Background_Worker_Sheet.png`, or (for a named recurring extra) `Featured_Extra_<Name>_Sheet.png` — the filename isn't enforced by the script, it's a human/agent-facing naming convention. Pass `--role "a background worker"` (or whatever fits — **role is always freeform text, never a hardcoded set of titles**, since every production's cast is different) so the prompt itself is clear about which character this sheet is for. A single Featured Extra sheet can hold multiple named characters as separate panels when a production has several recurring supporting roles (confirmed on Roman Gladiator: one sheet held both "Taurus" and "Brutus") — describe each named character distinctly in the `character_description` text passed in.

CLI: `python3 001_Architecture/Skills/Reimagined_Realms_POV_Shorts_Pipeline_v2/character_sheet_generation.py "<description>" --out "<path>" --role "<role>"`.

**Multi-character prompting — only applies to the `reference_image_urls` fallback path, NOT the normal `first_frame_url` path.** `shot_list_builder.build_multi_character_reference_note()` / `build_video_prompt()`'s optional `character_roles` param produce `@Image1 shows the main stoker. @Image2 shows a background worker.` (ByteDance's own ordinal-referencing syntax, confirmed live via BytePlus ModelArk docs, see Seedance-Prompting-Guide) — but since `first_frame_url` and `reference_image_urls` are mutually exclusive (confirmed 2026-08-08), there's no `reference_image_urls` array for these tags to point at when a scene already has its own first-frame image, which is this pipeline's normal case. Multi-character consistency for the normal path comes from the scene's first-frame image already having been generated correctly (both characters baked in via `input_urls` at the image-generation stage) — don't pass `character_roles` when also setting `first_frame_url`.

## Environment Sheet (rebuilt round 3 — one sheet per location, one panel per scene)

`environment_sheet_generation.py` — `generate_environment_sheet(location_name, scene_angles, output_path, aspect_ratio="16:9", resolution="4K", input_urls=None)`, where `scene_angles` is `[{"scene": int, "description": str}, ...]` — every scene that takes place in this location gets its own panel, one JSON file per location (e.g. `Ludus_Interior.json`, `Colosseum.json`). CLI: `python3 001_Architecture/Skills/Reimagined_Realms_POV_Shorts_Pipeline_v2/environment_sheet_generation.py "<location.json>" --out "<path>"`.

**Round 1's single combined production-wide sheet is gone.** It could not hold enough detail for a whole production, and worse, it silently merged scenes: on Roman Gladiator, two scenes set in the same cell got collapsed into one shared panel, which dropped an entire action beat (a door-push) that the merged scene never showed. `build_environment_sheet_prompt()` now hard-enforces one panel per scene, no reuse of another panel's exact framing, and no skipping ahead to an action's aftermath instead of showing the action itself — every rule directly traces to a confirmed failure, not theoretical caution.

**Strictly people-less, no exceptions.** No people, hands, arms, fingers, or held objects in any panel — not even distant/background/crowd figures. This took several regeneration passes on Roman Gladiator to actually enforce (hands on doors, distant crowd figures, held weapons kept creeping in) — the prompt now states this explicitly and repeatedly. Practice dummies/mannequins are not people and are fine. A production typically needs one environment sheet per distinct location (e.g. Ludus Interior + Colosseum), not one per production.

## Prop Sheet (front/back/held-from-POV per prop, round 2 adds hand-specific held panels)

`prop_sheet_generation.py` — `generate_prop_sheet(props, output_path, aspect_ratio="16:9", resolution="2K", input_urls=None)`, where `props` is a list of `{"name": str, "front": str, "back": str | None, "held_left": str | None, "held_right": str | None}` dicts. CLI: `python3 001_Architecture/Skills/Reimagined_Realms_POV_Shorts_Pipeline_v2/prop_sheet_generation.py "<props.json>" --out "<path>"`.

**Built after a confirmed failure:** the Roman Gladiator Prop Sheet only showed a shield's decorative front face, and every scene needing that shield in-hand rendered it backwards — a held shield's front always faces away from the carrier, so true POV only ever sees the back/strap side, and the model had no correct reference to draw from. Any prop with an asymmetric front/back or a specific carry orientation needs all applicable panels: **Front** and **Back** show the object alone (no hands, no people); **Held from POV (Left Hand)** / **Held from POV (Right Hand)** is the one deliberate exception — it shows the object gripped/worn by the specific hand named in its label, matching the actual first-person carry view. Omit `back` only for props with no meaningful distinct back (a flat coin); a prop only needs the `held_left`/`held_right` field(s) matching how it's actually carried (most props are carried in exactly one hand by convention, e.g. shield=left, sword=right).

**Round 2 fix (2026-08-08): a generic single `held` field is gone — always name the hand.** Confirmed failure on Roman Gladiator: a generic "Held from POV" panel with no hand specified rendered the Scutum Shield's grip with the wrong thumb orientation for its actual left-hand carry, because the model had a 50/50 chance of defaulting to right-hand grip anatomy. This is the same underlying laterality-guessing problem documented in the Seedance-Prompting-Guide's "Hand/limb laterality" section, just applied to a single-hand prop grip instead of a two-person contact point — same fix, name the hand explicitly, every time. Generate one Prop Sheet per production covering every recurring handheld/worn item.

**Every panel label is reserved its own margin, never overlapping the image.** Confirmed failure: an earlier pass had labels that could overlap panel content, defeating the point of the reference. `build_prop_sheet_prompt()` (and `build_environment_sheet_prompt()`) now explicitly instruct the model to place each label in a reserved blank strip beneath its panel.

## Storyboard (rebuilt round 2 for per-shot starting images, round 3 adds explicit combined sheet referencing)

`storyboard_generation.py` — `generate_storyboard(beats, output_dir, pov_lock=True, resolution="2K", input_urls=None)` generates **one individual full-resolution 9:16 image per beat** (`Panel_01.png`, `Panel_02.png`, ...) — not one combined grid image. Round 1 tried a single N-panel grid; that couldn't be reliably sliced into clean per-shot images afterward (unpredictable panel boundaries, resolution loss), so round 2 generates each panel as its own standalone image from the start. Each panel is POV-locked by default (`pov_lock=True` prepends the same strict first-person clause `shot_list_builder.py` uses) — **this lock is a per-call parameter, not hardcoded**, because this pipeline will get duplicated for other channels that may want conventional third-person storyboards (static cameras, dolly moves); pass `pov_lock=False` for those.

**Round 4 (2026-08-08): panel images always go into an `Assets/Images/Scenes/` subfolder, never loose in `Assets/Images/` alongside the reference sheets.** `generate_storyboard()` now creates `output_dir/Scenes/` automatically and writes every `Panel_NN.png` there — `Contact_Sheet.png` and the character/prop/environment reference sheets stay at `output_dir`'s root. This is enforced in code, not just a naming convention to remember: any one-off manual regeneration of a single scene (e.g. fixing a specific shot after review, as happened repeatedly on Roman Gladiator) should also target `Assets/Images/Scenes/` directly to match.

**No text is ever baked into the AI-generated panel image** — panel numbers, scene captions, etc. are never part of the image-generation prompt (image models render illegible/gibberish text — same rule as the "never use image model for labeled diagrams" convention elsewhere in this workspace). Instead, `compose_contact_sheet(panel_paths, captions, output_path)` deterministically composites a caption strip under each panel via PIL — Tony's requested format is `"Scene 1: Worker awakes"`, short and plain, for review only.

**Round 3: each beat can carry its own `input_urls` and `sheet_labels` in `Beat_Table.json`, overriding the production-wide default.** A scene's needed sheets change mid-production — a new location's Environment Sheet, a newly-introduced named extra's Character Sheet, a prop only some scenes carry — so per-beat overrides matter. `sheet_labels` is a plain-text list naming which labeled part of each attached sheet to use, e.g. `["Main Character Sheet", "Ludus Interior Environment Sheet, panel labeled SCENE 3", "Scutum Shield — Held from POV panel on the Prop Sheet"]`; `build_reference_sheet_note()` turns this into an explicit instruction appended to the prompt. **This is the only proven-working reference pattern — validated across two full test productions:** attach the whole sheet image as a reference (never crop a panel out of it — cropping AI-generated grids is unreliable, unpredictable panel boundaries and resolution loss, the same reason storyboard panels moved to individual generation), and name the specific label to use directly in the prompt text.

**Each panel IS a shot's starting image now** — pass its public URL as `first_frame_url` to that shot's `video_generation.generate_video()` call, no cropping or re-derivation needed.

CLI: `python3 001_Architecture/Skills/Reimagined_Realms_POV_Shorts_Pipeline_v2/storyboard_generation.py "<Beat_Table.json path>" --out_dir "<dir>" [--no_pov_lock]` — writes `Panel_NN.png` per beat into `<dir>/Scenes/`, plus `Contact_Sheet.png` at `<dir>`'s root for review.

## Scene-writing checklist (run before any scene description becomes a generation prompt)

Full checklist lives in `POV_Style_Guide.md` under "Scene-writing checklist" — anatomy/pose, camera-logic, action-mechanics (push vs. pull), POV-visibility (can't see your own shoulder/back/head), body-position-must-be-explicit ("looking up" alone is ambiguous between standing and lying), difficulty triage, and reference-conflict. Every item traces to a real confirmed failure from the Roman Gladiator test (scene 6's "hand on shoulder" rendered as a hand on the knee; scene 13's "looking up" victory pose rendered lying on the ground) — run it on every scene before writing the generation prompt, not just when something looks obviously wrong.

## Video Generation (rebuilt for Seedance 2.0; round 3 corrects first_frame_url/reference_image_urls to be mutually exclusive)

`video_generation.py` — `generate_video(video_prompt, output_path, first_frame_url=None, reference_image_urls=None, duration=5, resolution="720p", aspect_ratio="9:16")`. Runs Seedance 2.0 (`standard` mode, quality over speed per Tony's stated priority — "quality... should come first and foremost, and then speed, efficiency, and money saving are second priority") via `kie-cli bytedance_seedance_video`. `generate_audio=true` (carried over from v1's validated A/B test choice).

**Confirmed live 2026-08-08: `first_frame_url` and `reference_image_urls` are mutually exclusive on kie.ai's actual endpoint — passing both raises `ValueError` in `submit_video_task()` before ever hitting the API** ("The reference image and the first and last frames are mutually exclusive, and only one scene can be selected"). The round-2 note claiming both could be combined was never tested end-to-end and was wrong. **This pipeline's normal path uses `first_frame_url` alone** — pass that scene's own corrected image (from `storyboard_generation.py` / `Assets/Images/Scenes/`). Character/prop/environment consistency is already baked into that image at the image-generation stage (sheets were used as `input_urls` when the image itself was generated), so no separate `reference_image_urls` are needed or wanted on top of it. `reference_image_urls` (and `shot_list_builder.build_multi_character_reference_note()`/`character_roles` for `@Image1`/`@Image2` tagging) remain available only as a fallback for a shot with no first-frame image at all — not used by this pipeline's primary path.

**Video prompt content:** describe motion, camera movement, and sound only — never re-describe pose, hand laterality, or other static visual details already established in `first_frame_url`. This is a confirmed image-to-video prompting principle (see Seedance-Prompting-Guide's "Hand/limb laterality" section), not just a style preference — re-describing static details risks diluting the motion instruction or conflicting with what the frame already shows.

CLI: `python3 001_Architecture/Skills/Reimagined_Realms_POV_Shorts_Pipeline_v2/video_generation.py "<prompt>" --out "<path>" --first_frame_url "<scene_image_url>"`.

**Clip trimming:** `trim_to_best_window()` — unchanged from v1, same middle-window heuristic.

## Known open questions / fallback paths (do not treat any of this as locked)

Tony was explicit that none of the following are final decisions — they're the recommended starting point, chosen only because "I can't give you a solid answer until I really see the results":

1. **Reference images per shot — resolved 2026-08-06, superseded.** Round 1 (character+environment sheets only, no per-shot image) tested on Titanic Stoker and produced real drift (see Round 2 update at the top of this file). Round 2 adds `first_frame_url` sourced from each shot's own storyboard panel — this is now the default, not a fallback.
2. **Storyboard granularity — resolved 2026-08-06, superseded.** The single-combined-grid approach was replaced entirely; each panel now generates individually at full 9:16 resolution, so the "too much detail for one grid" risk no longer applies.
3. **Environment sheet granularity — resolved 2026-08-08, superseded.** One combined sheet was confirmed insufficient (see Round 3 update above). Now one sheet per location, one panel per scene — this is the default, not a fallback.
4. **Multi-character reference tagging — new, unverified 2026-08-06.** `@Image1`/`@Image2` ordinal referencing is a documented ByteDance capability (see Seedance-Prompting-Guide), wired into `build_video_prompt()`, but not yet confirmed to produce visibly distinct faces in an actual Seedance 2.0 output from this pipeline — test on shot 9 (the Titanic Stoker duplicate-faces shot) before relying on it broadly.
5. **Prop sheet held-panel hand/arm consistency — new, unverified 2026-08-08.** The "held from POV" prop panel is meant to match the production's Main Character Sheet's hand/forearm appearance, but this hasn't yet been confirmed to actually render consistently across the two — pass the Main Character Sheet as an `input_urls` reference when generating a prop sheet to test this.

Before locking any of these in for real production use, run a full test, compare against the v1 Pyramid Builder identity-drift baseline via Video-Analyzer, and get Tony's read on the result.
