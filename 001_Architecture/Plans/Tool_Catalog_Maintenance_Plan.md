# Tool Catalog Maintenance Plan

> **Date:** 2026-10-08
> **Status:** Draft for discussion with Tony. Nothing here is built yet.
> **Owner:** Tony
> **Written by:** Claude Code (opus-deep worker)
> **Goal:** Keep the Tool Catalog current without Tony touching it, and make every future agent session actually check it before saying "I don't know a tool for that" or offering to build something from scratch.

---

## 0. The short version

1. **Move the source of truth out of the artifact.** Keep one JSON file in the repo as the master list. The artifact page becomes a view that gets regenerated from that file. Cron jobs and scripts can't edit a claude.ai page, but they can edit a file.
2. **Split the upkeep into a free part and a judgment part.** A daily script spots new bookmarks and costs nothing. Deciding whether each one is a real tool takes judgment, so a cheap worker (`delegate.py`) does it in batches. Republishing the page needs a live Claude session, so it happens at session close.
3. **Ingest still files each bookmark, but tools get no extra notes.** The catalog is the index and the Resource Library is the shelf. One bookmark becomes one note. A tool that is only mentioned inside a video gets a catalog row that points at that video's note, not a note of its own. This answers the bloat worry (section 3).
4. **Videos come in three tiers of cost.** Most YouTube bookmarks already have the description and full transcript clipped (58 of 72 in `000_Ingest/` today), so the tools they mention can be pulled from text cheaply. Video-Analyzer runs only on the few videos where tools appear on screen without being named.
5. **Graphify can't answer "find me a tool for X", and the reason is mechanical.** Its search only looks at headings and filenames, never at the summary that says what a tool does. For this question the catalog should replace Graphify, not feed it (section 5).
6. **The laziness fix is a rule plus a visible receipt.** Add a new Rule #1b next to Graphify's Rule #1, run through the Tool-Manager skill, which is already set to auto-invoke. Every tool answer has to start with a line showing that the catalog was searched, so Tony can see at a glance whether the check happened (section 6).

## 1. Canonical data location and format

### What exists today (and why it can't be the source of truth)

| Thing | Where | Problem |
|---|---|---|
| Tool Catalog page | https://claude.ai/artifact/3D9QHYnL7EZ8eunDsHRz4R | Hosted on claude.ai, so only a live Claude session can update it. A cron job can't write to it. |
| Page source HTML | session scratchpad `.../scratchpad/ingest_tool_catalog.html` | Temporary. It disappears with the session. It can always be recovered with `Artifact read` on the URL, so there's no emergency. |
| The data itself | a hardcoded `const DATA = [...]` array inside the HTML | Each row has only 4 fields: `[name, description, source filename, "ingest"/"library"]`. **There are no URLs**, so duplicates can't be detected reliably and nobody can click through to the tool. |
| Scan reports | `001_Architecture/Audit_Reports/*_Scan_2026-10-08.md` (3, the third still running) | Point-in-time snapshots. They're good seed data but shouldn't be edited going forward. |

### Recommendation: a JSON master file plus a generated Markdown view, both in the existing Tool-Manager folder

No new folder is needed. Everything goes in folders that already exist.

| File | Role | Edited by |
|---|---|---|
| `001_Architecture/Tools/Tool-Manager/data/Tool_Catalog.json` | **Source of truth.** One record per tool. | Scripts and agents, never by hand-editing the HTML |
| `001_Architecture/Tools/Tool-Manager/data/Tool_Catalog.md` | Generated readable view, grouped by category, one line per tool. This is what an agent reads to answer "find me a tool for X". | Generated by script only |
| `001_Architecture/Tools/Tool-Manager/data/Tool_Catalog_Ledger.json` | List of every file that has been scanned, with its verdict (has tools / no tool / waiting on video / needs review). Stops the same file from being judged twice. | Scripts and agents |
| `001_Architecture/Tools/Tool-Manager/Tool_Catalog_Page.html` | Durable copy of the artifact page. It's a static template that reads `Tool_Catalog.json` as a supporting file, not a hardcoded array. | Changed rarely, by a Claude session |
| `001_Architecture/Tools/Tool-Manager/tool_catalog.py` | One script with subcommands: `scan`, `find`, `add`, `relink`, `render`, `status` | Code (the `.py` name stays lowercase to match the folder's other scripts, per the naming rule's "would it break" exception) |

**Why Tool-Manager's folder?** Tool-Manager is already the workspace's "what tools do we have" layer, and its skill is already marked *MANDATORY AUTO-INVOKE* before any tool question. Putting the catalog there lets it ride a trigger that already exists, and the `tm` command can get a `tm find` subcommand. It also completes a three-level picture that makes sense:

| Layer | Answers | File |
|---|---|---|
| TOOLBOX.md | "What do we have **installed**?" | `TOOLBOX.md` |
| API Directory | "What's **connected**, with keys and caps?" | `001_Architecture/API_Directory.md` |
| **Tool Catalog** | "What have I **bookmarked** but not adopted yet?" | `Tool_Catalog.json` |

### Proposed record shape

```json
{
  "id": "opusclip",
  "name": "OpusClip",
  "url": "https://clip.opus.pro/",
  "kind": "saas",
  "category": "YouTube / Content",
  "does": "Turns long videos into short viral clips with captions and vertical reframing.",
  "use_for": ["long-to-short", "clipping", "auto-captions", "vertical-reframe"],
  "pricing": "freemium",
  "status": "bookmarked",
  "sources": [
    {"path": "007_Resource_Library/Tools/Opusclip.md", "via": "library", "seen": "2026-09-05"},
    {"path": "007_Resource_Library/Affiliate_Marketing/OpusClip-Affiliate-Program.md", "via": "library", "seen": "2026-09-20"}
  ],
  "first_seen": "2026-09-05",
  "notes": ""
}
```

- **`kind`** covers Tony's broad definition of a tool: `saas`, `github-repo`, `skill`, `plugin`, `mcp`, `api`, `desktop-app`, `browser-extension`, `resource-site` (downloadable assets, graphic examples, prompt libraries), `model`.
- **`use_for`** holds plain-language job words. This is the field that makes "find me a tool for X" work. It describes the job the tool does, not just its name.
- **`status`** is `bookmarked`, `trying`, `adopted`, `rejected` or `dead`. When a tool is adopted, its row stays with `status: adopted` plus a pointer to TOOLBOX or the API Directory. It isn't removed, so the history survives. This is a small change to API_Directory.md line 111, which currently says "removed/marked done".
- **The file has a `meta` block** holding `updated`, `artifact_url`, `last_published` and `published_hash`. When the current hash differs from `published_hash`, the live page is out of date.

### How the artifact relates to the master file

The page is generated from the JSON, never edited by hand. Republishing means a Claude session runs `tool_catalog.py render` and then calls the Artifact tool. It publishes `Tool_Catalog_Page.html` to the same URL, with `Tool_Catalog.json` as a supporting file, and the page loads the data from that file. That one call is the only step that has to happen inside a live Claude session.

## 2. Update mechanism

### What can be a simple cron script and what needs judgment

| Step | Needs judgment? | Mechanism | Cost |
|---|---|---|---|
| Spot new or changed files in the watched folders | No | cron, daily | Free |
| Pull out URLs, GitHub `owner/repo` and product domains from each file | No | same script (regex) | Free |
| Check against the catalog by URL, GitHub repo and name | No | same script | Free |
| Pull tool names from YouTube descriptions and transcripts | **Yes**, but text only | `delegate.py` worker, in batches | Pennies per batch on the capped chores key |
| Decide whether this is a real tool, and write `does` / `use_for` / `category` | **Yes** | `delegate.py` worker, same batch | Same as above |
| Find tools that are shown on screen but never named | **Yes**, needs vision plus a person reading frames | Video-Analyzer in a Claude session, gated (section 4) | Real cost, so it's rationed |
| Republish the artifact page | No, but only a live session can do it | Claude session, at close-out | Free |

### What gets watched

| Folder | Why | Notes |
|---|---|---|
| `000_Ingest/*.md` (top level only) | Where new bookmarks land | Subfolders are skipped. They're project bundles and drop zones, matching how the ingest skill and the first scan treated them. |
| `007_Resource_Library/**/*.md` | Catches anything ingest routes, including screenshot notes that `process_image_ingest.py` writes straight into `Tools/` without going through `000_Ingest/` | The first full pass is the seed. After that, only new or changed files. |

**Not watched:** installed skills and plugins. TOOLBOX.md and `Skill-Index.md` already track those. A bookmarked skill repo that isn't installed still gets cataloged, from the bookmark.

### The daily detector (`tool_catalog.py scan`)

This copies the `sync_plans_to_todo.py` pattern that's already running: mechanical only, it flags things and never makes decisions.

1. Walk the watched folders. Skip every file whose path plus content hash is already in the ledger.
2. For each new file, pull out every URL, GitHub repo, product domain and title.
3. If a URL or GitHub repo already matches a catalog entry, add the file as a new `source` on that entry, mark it `matched` in the ledger, and stop there.
4. If the file has a YouTube link, mark it `video` in the ledger and record whether a `## Transcript` section exists.
5. Everything else goes into the ledger as `pending`.
6. Write a one-line log entry. Never move, rename or delete anything.

Proposed crontab line, next to the existing 6am plans sync:

```bash
30 6 * * * /opt/homebrew/opt/python@3.14/Frameworks/Python.framework/Versions/3.14/bin/python3 /Users/tonymacbook2025/Documents/Agent-OS/001_Architecture/Tools/Tool-Manager/tool_catalog.py scan >> /Users/tonymacbook2025/Documents/Agent-OS/001_Architecture/Tools/Tool-Manager/tool_catalog.log 2>&1
```

### Classification (judgment, done in batches)

`delegate.py` runs a cheap worker that reads a written procedure and processes every `pending` and `video` file in the ledger:

- **Real tool?** If yes, it adds a catalog row with `does`, `use_for`, `kind`, `category` and `url`.
- **Video bookmark?** It runs the Tier 1 text extraction from section 4.
- **Not a tool** (a plain tutorial, news, a personal note)? It marks the file `no-tool` so it's never looked at again.
- **Unsure?** It marks the file `needs-review`, and the item goes on a short list for the next Claude session to show Tony.

Then it runs `tool_catalog.py render` so the Markdown view is current.

New bookmarks arrive at about 5 to 40 a week and come in bursts (59 arrived on 2026-09-26 alone), so one batch a week or one per session is enough. **When to trigger it is an open decision (D3).**

### Keeping file paths correct when ingest moves files

Ingest moves files from `000_Ingest/` to `007_Resource_Library/` and renames them, so catalog `source` paths would go stale. There are two fixes, and both should be used:

1. **The ingest skill updates the path itself.** Add a step: after routing a file, run `tool_catalog.py relink "<old path>" "<new path>"`.
2. **The detector repairs anything that slips through.** Any `source` path that no longer exists gets re-matched by URL or title. Anything it can't match is listed as an orphan for review.

### A prerequisite that makes all of this reliable: add the page URL to the Web Clipper template

None of the 159 bookmark files in `000_Ingest/` has frontmatter, and the clipper doesn't record the page's own URL. Today, matching non-YouTube bookmarks means guessing from image or asset URLs inside the page body. Adding `source: "{{url}}"` to the Obsidian Web Clipper template (Tony changes this in the clipper's settings) makes matching exact for every future bookmark. **This is the highest-leverage small change in the plan (D6).**

## 3. Should a cataloged tool still go through ingest? (Tony's open question)

### Recommendation: yes, ingest still files the bookmark. But each bookmark becomes one note, tools never get extra notes, and the catalog row points at that one note.

### Reasoning

**1. Ingest doesn't actually duplicate tool bookmarks, because it moves them.**
Under the ingest skill (Step 4), a tool bookmark is moved into `007_Resource_Library/Tools/` with frontmatter added, *instead of* getting a separate wiki page. So "catalog plus ingest" doesn't make two copies. You end up with one note on the shelf and one line in the index. The duplication Tony is worried about mostly isn't happening.

**2. Skipping ingest would leave the evidence somewhere temporary.**
`000_Ingest/` is never committed to git and never graphified, by design. If a tool lived only in the catalog, its backing evidence (the description, transcript, links and screenshots) would sit in an unbacked-up staging folder that's meant to be emptied. The catalog row would be a pointer to nothing. A catalog line holds about 20 words, and the note holds everything else.

**3. Tony is right about where the real bloat risk is, but it's somewhere else.**
The risk is **creating a separate stub note for every tool mentioned somewhere.** One YouTube video like "5 GitHub repos that print $$$" names five tools. The bloated version is the video's note plus five new `Tools/` stubs. The lean version is the video's note (filed to `Tutorials/`) plus five catalog rows whose `source` points at that note. **Rule: a mention gets a catalog row, and only a bookmark gets a note.**

**4. The catalog should actively reduce the bloat that already exists.**
The Resource Library already has clusters of duplicates: n8n has 13 notes, Arcads 6, Nano Banana 8, TubeGen AI 7. When a new bookmark matches a tool that's already cataloged, ingest should add a "Also seen in" link to the existing note instead of filing a second near-duplicate note. **What happens to the duplicate file is an open decision (D2).** Agents can't delete, so the choices are moving it to `Archive/` or keeping both.

### What changes in the ingest skill (proposed, not done)

- **Step 1 (classify):** before classifying, run `tool_catalog.py find --url <url>`. A match means duplicate handling (D2), not a new note.
- **Step 3 (route):** after moving a file, run `tool_catalog.py relink`.
- **Step 4:** add one sentence: "Never create a separate note for a tool that is only *mentioned* inside another note. Add a catalog row pointing at the parent note instead."
- **Step 7, found while reading:** the ingest skill still says `graphify update .` from the workspace root. That contradicts REGISTRY.md and AGENTS.md, which both say never to run graphify on `.` and to update only the domain folder (`graphify update 007_Resource_Library`). Fix it in the same edit.

## 4. Video handling

Most of Tony's video bookmarks don't need Video-Analyzer at all. The Web Clipper already saves the description and a timestamped transcript. Today, 58 of the 72 YouTube bookmarks in `000_Ingest/` have a `## Transcript` section. The tool links are usually in the description (for example, "5 GitHub repos that print $$$" lists all five GitHub URLs), and the tool names are usually spoken.

### The three tiers

| Tier | What it does | When it runs | Cost |
|---|---|---|---|
| **0: links** | Regex pulls GitHub, product and affiliate links out of the description | Every video, in the daily cron | Free |
| **1: text** | The worker reads the description and transcript, lists the named tools, and judges whether the video is "about tools" or a plain tutorial | Every video, in the classification batch | Cheap (text only) |
| **1b: missing transcript** | `yt-dlp --write-auto-subs --skip-download` pulls captions so Tier 1 can run (yt-dlp is already installed, per TOOLBOX) | The 14 videos with no transcript, and any new ones | Free |
| **2: on-screen** | Video-Analyzer with `--category screen-text` and a raised `--threshold 0.5`, so screen recordings don't produce too many cuts | **Only when it's worth it** (below) | **Expensive**: Gemini API time, plus the skill's required step where an agent reads every keyframe |

### When a video gets Tier 2

The Tier 1 worker flags a video for Tier 2 only if both of these are true:
- the transcript points at tools without naming them ("this site right here", "this repo", "I'll show you the tool"), or the video is clearly a tool roundup with fewer named tools than it promises, **and**
- the video looks like it's about tools, not a plain how-to.

Flagged videos go into a `video-tier2` queue in the ledger. They're **not** run automatically. A Claude session shows Tony the queue ("3 videos might show unnamed tools on screen. Run them?"), and Tony approves (D4).

### Being honest about what can't be automated

Video-Analyzer can't be fully automated, and its own skill file says so: the step where an agent views every keyframe "cannot be scripted". Running it on every video bookmark would cost real money and session time to recover a handful of tools that Tier 1 mostly catches already. The tiers above should cover most video-borne tools at close to zero cost. Tier 2 handles the remainder by exception.

Plain tutorials with no tool in them get marked `no-tool` in the ledger. They aren't catalog entries. They still go through normal ingest to `Tutorials/`.

## 5. The Graphify question

### Why Graphify hasn't answered "find me a tool for X"

These causes were checked directly against the live Resource Library graph (10,149 nodes) and the graphify 0.9.55 source code, not guessed.

1. **The search never reads what a tool does.** `graphify query` picks its starting nodes by matching the query against each node's **label, node ID and source file path** only (`graphify/serve.py`, the `fields = (norm_label, label_tokens, nid_text, source, source_tokens)` line). The `summary:` frontmatter that describes the tool is stored on the node but **never searched**. `Tools/Opusclip.md` has the label `Opusclip.md`. Its summary says "transforms long videos into short, viral-ready clips", and the search can't see that.
2. **Live test.** `graphify query "what tool can turn long videos into short clips"` returned a Seedance prompting guide section, a TradingView MCP note and a Canva help page. **OpusClip, Ssemble and Overlap are all in `Tools/` and none of them came back.** Searching the exact name `"OpusClip"` landed on the *affiliate program* note, not the tool note.
3. **The "fuzzy relations" are thin.** 6,723 of the 7,911 edges (85%) are `contains` edges, meaning page-to-heading structure. Only 328 are `semantically_similar_to`. `Opusclip.md` sits alone in a one-node community (#2096). There's almost no path from a *need* to a *tool* for the graph to follow.
4. **New notes never get semantic links.** The Stop hook (`Graphify/hooks/rebuild-dirty.sh`) runs only `graphify update`, which is AST-only with no AI step. Semantic edges come only from a manual `/graphify --update`, last run on the Resource Library around 2026-09-15 to 09-19.
5. **Ingest bookmarks are invisible on purpose.** `000_Ingest/` is excluded from graphify, so about 126 tools found there can't be reached. The Tools subfolder also dropped about 12% of its files during the original extraction (REGISTRY.md v2.1 note).

### Recommendation: for this one question, the catalog replaces Graphify. Graphify keeps everything else.

"Find me a tool for X" is a **lookup-table problem**: return a ranked list of named things with what they do. Graphify is built for **relationship questions**: how does X connect to Y, where is X documented, what depends on Z. Making Graphify do capability search would mean paying for a semantic re-extraction and still being limited by search that only matches labels. That's the wrong tool for this job.

- **Replace:** for tool-finding questions, the catalog comes first (Rule #1b below).
- **Light complement, free:** `Tool_Catalog.md` lives in `001_Architecture/`, which the Architecture graph already indexes. A Graphify query for a tool's *name* can land there, but nobody depends on that.
- **Not recommended:** feeding catalog data into Graphify as a source, or rewriting Tools/ note headings to carry capability words. Both are costly for little gain.

## 6. The reliability fix (the "too lazy to look" problem)

### Why a rule alone isn't enough, and what to add

Rule #1 (Graphify first) works partly because it names an exact command. A tool rule needs the same: an exact command, an exact file, and **a visible receipt in the answer**. The receipt does the enforcing. If a tool answer doesn't open with the catalog line, Tony knows the check was skipped and can say so in one word.

### Where it goes (recommendation)

| Place | Change | Why |
|---|---|---|
| `~/.claude/CLAUDE.md` (global) | Add **Rule #1b** right after Rule #1 (text below) | Always loaded, unlike skill descriptions, which get skipped |
| `AGENTS.md` and `GEMINI.md` (workspace root) | The same rule, worded for Codex and Gemini | Every harness behaves the same |
| `Tool-Manager/SKILL.md` | Add trigger (5) "recommending a tool, or saying none exists" to the description, plus a "Bookmarked tools (Tool Catalog)" section with the lookup steps and the classification procedure | Uses the auto-invoke that already exists. No new skill folder needed |
| Workspace `CLAUDE.md`, "BEFORE BUILDING ANYTHING" | One line: "…and check the Tool Catalog (`tm find`) before proposing to build" | Covers the "let's build it" path, not just the "recommend" path |

Per standing feedback, agents can't edit `~/.claude/CLAUDE.md` in auto mode, so Tony applies that edit or approves it.

### Draft rule text (proposed, for `~/.claude/CLAUDE.md`)

```markdown
## RULE #1b: "IS THERE A TOOL FOR X?" — CHECK THE TOOL CATALOG FIRST

Before you (a) recommend any tool, app, repo, skill, plugin, API or resource site,
(b) say you don't know of a tool for something, or (c) propose building a script,
app or skill from scratch — you MUST search Tony's Tool Catalog (every tool he has
already bookmarked). For tool-finding questions this comes BEFORE Graphify (Rule #1):
Graphify does not index what tools do.

1. TOOLBOX.md — is it already installed? (Rule #3)
2. Run, with 2–3 different phrasings of the need:
   /Users/tonymacbook2025/Documents/Agent-OS/001_Architecture/Tools/Tool-Manager/tm find "<the job in plain words>"
3. Read the matching category section of
   /Users/tonymacbook2025/Documents/Agent-OS/001_Architecture/Tools/Tool-Manager/data/Tool_Catalog.md
   in full — keyword search misses synonyms, and one category is short.
4. Only then: web search, or propose building.

Show the receipt. Your answer starts with one line:
  Tool Catalog: checked "<phrasing 1>", "<phrasing 2>" — N matches
then lists the matches (name — what it does — link — status) before any outside
suggestion. Zero matches? Say so explicitly. No receipt line = the rule was skipped.
```

### Optional extra (not recommended to start)

A `UserPromptSubmit` hook could detect phrases like "is there a tool", "recommend an app" or "something that does" and inject a reminder. Standing feedback says to prefer explicit triggers over automatic inference and to check that a classifier actually has the signal before relying on it. So start with the rule plus the receipt, and add the hook only if receipts still go missing after a couple of weeks.
