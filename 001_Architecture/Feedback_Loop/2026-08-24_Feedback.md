# 2026-08-24 Feedback Log

(continuation of the 0002_Mantis_Shrimp_Color_Vision overlay-build session that started 2026-08-23 — full iteration-by-iteration breakdown lives in `Data/Report_Card.md` for that production; this file captures the durable standing rules extracted from it)

## Use the Real Asset as the Generation Reference, Never a Verbal Description of It

When Tony described an existing asset in casual terms ("zeros and ones") for a full-bleed regeneration request, that description was reinterpreted literally (generated actual digit typography) instead of using the real existing asset file as an image-to-image reference. Tony's correction: "you misunderstood me... use the attached signal pattern... don't take it literally."

**Why:** Verbal descriptions of existing visual assets are explanations for a human, not generation specs — the real file is always more precise than a paraphrase of it.

**How to apply:** Whenever a request references an existing asset ("make this X full-bleed," "animate this," "use this same look"), locate and pass the actual file as the generation reference before writing any text-only prompt from a description of it.

## Grounded Coordinates Are Necessary, Not Sufficient, for Good Label Layout

`detect_label_coordinates.py` (Gemini vision) correctly identified the real feature pixel for a label anchor, but the resulting on-screen layout still failed — text ran off-screen near a frame edge, and another label sat directly over the diagram art it described. Tony: "arrows and overlays are either partially off screen or... hard to read because the labels are directly over some of the imagery... are you not looking at these frames and examining them?"

**Why:** Accuracy (pointing at the right feature) and layout quality (readable, non-overlapping, on-screen) are two separate checks — grounding solves the first, not the second.

**How to apply:** After any label/callout placement, look at (or measure) the actual rendered frame at that label's visible timestamp — check screen-edge margin and negative-space placement — before considering it done. See `Diagram-Generation` SKILL.md for the full checklist now written in.

## Static Mockups Before a Remotion Re-render — Tony's Own Suggested Fix, Now Standard

When the first label layout missed, Tony asked: "why don't you either show me a rendering of what those frames should look like or do some better research... before you re-edit those scenes in Remotion." Drawing the corrected layout directly onto already-extracted real frames (cheap, fast) and getting sign-off before touching the Remotion component saved multiple full-render iteration cycles — two more rounds of pixel-level correction happened at the mockup stage, which is far cheaper than at the render stage.

**Why:** A positioning fix is much cheaper to iterate on a static image than a rendered video composition.

**How to apply:** Any time a visual layout needs correcting, build a fast static mockup on a real frame first, get approval, then implement for real — now written into `Diagram-Generation` SKILL.md as standard practice.

## "The Very End of the Audio" ≠ "The Very End of the Video"

Asked to fix an abrupt fade at "the very end of the audio," the literal last video frame was checked first and found already silent — the actual audio content (narration/music) stopped dead ~10 seconds earlier, right at the boundary into a silent end card. The real fix was a fade ending at that boundary, not at the file's last timestamp.

**Why:** A trailing silent card/tail means "the end of the audio" and "the end of the video" are different timestamps — conflating them would have missed the actual problem entirely.

**How to apply:** Before fixing an audio-fade complaint, measure where the real (non-silent) audio content actually stops, don't assume it's the file's final frame.

## RMS Verification Method — astats+grep Is Unreliable, Use Raw PCM + numpy

An initial audio-continuity check via `ffmpeg -af astats` parsed through a shell grep returned identical peak/RMS values across clearly different timestamps — silently wrong. Switched to extracting short raw-PCM WAV segments and computing RMS directly in Python/numpy, which gave correct, differentiated readings and caught the real silence gap.

**Why:** `astats`' log-formatted summary output isn't reliable to parse via shell text tools for this kind of point-in-time check.

**How to apply:** Any future audio-level verification should extract PCM and measure with numpy, never `astats` piped through grep. Now the locked method in `Anomalous_Wild_Video_Pipeline` SKILL.md Phase 8.

## End Card Needs a Spoken CTA by Default — Not Just Visual Text

The Anomalous Wild end card shows "Like, Comment" as on-screen text but had no spoken call to action, and — separately — played under total audio silence. Tony asked for a CTA voiceover using the production's own ElevenLabs voice, sized to fit the end card's ~10s runtime.

**Why:** A silent end card with only visual text is a missed engagement opportunity, and every video was shipping this way by default until flagged.

**How to apply:** Every Anomalous Wild production's end card now gets a generated CTA VO as a standard pipeline step (added to `Anomalous_Wild_Video_Pipeline` SKILL.md Phase 7), not a one-off fix.

Tony's explicit framing: capture every iteration, every liked/disliked piece of feedback, and why things changed — not to document history for its own sake, but so future productions across every channel start closer to the target grade with less back-and-forth, working toward largely autonomous pipeline runs. **How to apply:** Every mistake this session that had a generalizable cause got written into the actual skill file governing that step (Diagram-Generation, Anomalous_Wild_Video_Pipeline), not just logged here — skills get followed automatically on future runs; a memory note only gets consulted contextually. Prefer skill-file edits over log entries when a lesson is meant to change future default behavior.

## Thumbnail Text/Arrow Overlay: Composite With the Image Model, Never Hand-Coded PIL Coordinates

First attempt at adding headline text + a pointer arrow to a finished thumbnail used PIL with eyeballed pixel coordinates for the subject's eyes and a formula-driven bezier arrow. Result: arrow tip landed on the neck/joint instead of the eyes, and one arrowhead clipped into the headline text — because PIL has zero actual visual understanding of the image it's drawing on top of, it's just math against guessed coordinates. Tony: "You really should have references from the last video... why does your vision not really inspect those things?"

**Why:** The channel's one existing finished example (`0001_Bioluminescence_Weapon`'s "this fish hunts with light" thumbnail) was never actually produced by the pipeline script — `generate_youtube_package.py` explicitly prompted "no text, no captions." That finished thumbnail was hand-built in a past session and the textless base concepts were the only thing the automated pipeline ever actually produced. Checking that real reference file (not just the JSON template spec) revealed the gap and the right fix: feed the base concept into `gpt-image-2-image-to-image` with a prompt describing exact headline text and arrow target, letting the model compose with real visual understanding of subject edges — not post-hoc pixel math.

**How to apply:** Never build text/arrow overlays with PIL/hand-coded coordinates on a photoreal image. Always run the treatment as an image-to-image edit pass on the base concept, and always locate and check any real finished example from a past production before assuming a template spec alone describes the actual target. Now the locked stage-2 method in `generate_youtube_package.py` and `Anomalos_Wild__Thumbnail_Style.json` (template v2, locked 2026-08-24).

## Thumbnail Template v2 Locked: Darkened Real Background, Not Flat Gradient — and Auto-Generated Headlines Approved

After the image-to-image fix above, first full-image-to-image pass replaced the busy photoreal background entirely (converged all 3 concepts toward a similar generic scene, losing the distinct per-concept mood). Tony's fix: darken the *original* background ~50% rather than replacing it — "I like the images that you just generated... but they should be darkened basically by 50% and then yes add the glow as well." Also confirmed per-concept glow-color variation is wanted (on-brand consistency through *structure*, not one fixed color), and explicitly approved automatic headline generation going forward — no longer wants to review headline copy himself, having seen this batch's quality ("colors we can't see," "these eyes shouldn't work," "it sees 16 colors").

**Why:** A flat gradient/solid-color background (the original v1 template) loses the real photo's texture and looks generic; darkening the real photo ~50% keeps it recognizable while still making the subject and text pop, per Tony's explicit side-by-side preference. Per-video glow-color variation plus fixed structural treatment (darken %, text style, arrow style) is the intended brand-recognition mechanism — consistent shape, varied color, per Tony: "when somebody comes to my YouTube page... it's kind of like on brand identity."

**How to apply:** `Anomalos_Wild__Thumbnail_Style.json` is now template v2 (locked 2026-08-24) — darken background ~50% (never flatten to gradient), glow color varies per concept, headline auto-generated by Claude each production (2-6 words, lowercase, curiosity-gap, tied to the video's actual hook fact) with no Tony review required by default. `generate_youtube_package.py` now runs both stages (base concept + treatment edit) automatically per call, taking `--headlines` and `--arrow-target` as Claude-authored inputs rather than deriving copy from weak string templates.
