## Session: Anomalous Wild Video Pipeline build via subagent-driven-development (Jul 7-8, 2026)

### Confirmed approach: subagent-driven-development for an 11-task plan, with real per-task review loops
Tony chose "Option 1 (subagent-driven)" when offered the execution choice after PLAN.md was approved. This was followed exactly as specified: fresh implementer subagent per task, task-scoped reviewer subagent (spec compliance + code quality verdicts), fix-and-re-review loops when issues were found (happened on Tasks 5, 6, 7, 8, 11), then one final whole-branch review at the end. Validated approach — worth repeating for future multi-task plans in this workspace rather than executing inline.

### Real-world stakes changed how a finding got resolved (Blotato account ID)
Task 8's reviewer flagged that identifying the correct Blotato accountId via process-of-elimination + spelling-similarity ("Anomalos Wild" vs "Anomalous Wild") was insufficiently rigorous given the real consequence: a wrong ID would publish a future video to the wrong YouTube channel. Rather than accepting the inference or digging for more (nonexistent) API-level corroboration, the direct move was to ask Tony to confirm the specific ID by name. He confirmed immediately (42514, "Anomalos Wild" is just a Blotato-side typo). **Pattern to repeat:** when a finding's real-world consequence is irreversible/high-stakes (publish-target, financial, destructive), and the available evidence is inference rather than ground truth, ask the human directly rather than trying to out-reason to more confidence — this closed the loop faster and more reliably than any additional API digging would have.

### The final whole-branch review caught real bugs no per-task review could have caught
Two genuine integration bugs only surfaced when reviewing the whole build together, after every individual task had already passed its own review:
1. Task 5's `not_found` coordinate-stripping (correct, approved in isolation) was rejected by Task 6's *original* required-field Zod schema (also correct, approved in isolation) — the two only contradicted each other when composed, and would have crashed diagram assembly exactly in the "never guess a coordinate" safety-path scenario the whole sub-pipeline was built to handle.
2. The plan's "no static frame >3-5s" rule was recorded as data (`max_static_s` in Beat_Table.json) across three separate places (Task 3 producer, Task 6 consumer-that-can't-consume-it, SKILL.md soft mention) but never actually mechanically enforced anywhere.
**Validated lesson:** per-task review is necessary but not sufficient for a plan where later tasks consume earlier tasks' real output shapes — always run the final whole-branch review on the complete file set, not just as a formality. Both bugs were fixed and re-verified before commit.

### A YAML frontmatter bug was actively degrading a live skill's trigger-matching, discovered via direct observation not just parsing
Task 11's SKILL.md had a malformed frontmatter (`description:` correctly quoted, but a second `<example>` block left dangling, unquoted, outside it). This wasn't just a theoretical YAML-parser complaint — it was proven to actively break the real system by comparing this session's own live skill-list display before and after the fix: before, the skill showed only its bare markdown H1 as a fallback description; after, it showed the full, rich trigger-phrase description. The exact same defect existed in Reimagined Realms' `SKILL.md` (same pattern, likely copy-pasted from an early template) — flagged to Tony, who asked for it to be fixed too, done and verified the same way.
**Pattern worth remembering:** `validate_build.py`'s `check_skill()` does a naive string search for `'name:'`, not real YAML parsing — it will report PASS on a SKILL.md with genuinely broken frontmatter. When a SKILL.md's frontmatter is suspect, verify with `python3 -c "import yaml; yaml.safe_load(...)"` directly, and cross-check the live skill list's actual displayed description as real-world proof, not just the parser's verdict in isolation.

### Cost-bearing steps (real API calls) proceeded without per-call permission-asking, since they were already-approved plan content
Several tasks required real, small-cost API calls (ElevenLabs TTS, kie.ai image generation ×2 tasks, Gemini vision) as explicit verification steps already written into the Tony-approved PLAN.md. These were run without re-asking permission each time, since the plan itself was the approval. Confirmed as the right call in this session — no pushback from Tony on any of these calls happening.
