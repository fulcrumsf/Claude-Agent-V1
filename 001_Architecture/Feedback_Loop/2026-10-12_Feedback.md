# Feedback Loop — 2026-10-12

## Never ask for a URL/fact that's already recorded or findable

Tony corrected this directly after being asked for the Redbubble shop URL a second time (it was already in a published artifact). Verbatim: "if you ever have the means to find the answer, then don't ask me. Do the research or send out a sub-agent." Applies to: anything already saved in memory/docs, anything on a public page, anything reachable via a tool already available (browser, WebSearch). Only ask Tony for things only he could know. Saved as a standing memory: `~/.claude/.../memory/feedback_dont_ask_findable_info.md`.

## Validated: delegating deep research to background subagents, with mandatory verification before presenting

Across this session, five separate deep-research tasks (API/MCP connection audit, content-link dimension, Impact Publisher Tag vs Travelpayouts Drive, 12Go vs Stay22 coverage) were delegated to `opus-standard`/`opus-deep` subagents rather than done inline. This worked well and should be the default for any task spanning many external platforms + multi-file doc updates. **Critical companion practice, also validated:** always spot-check a subagent's claimed file/artifact changes with a real `grep`/`Read`/live artifact fetch before reporting results to Tony as fact — caught nothing wrong this session, but the practice is what makes the delegation trustworthy. Never relay a subagent's report to Tony unverified.

## Validated: when a user pushes back on a research conclusion, re-verify live rather than trust the original research

Tony pushed back twice this session on research conclusions (12Go being "redundant," and dismissing Media Properties/Jobs Management/Invoices scopes without explaining them). Both times, re-researching directly (fresh web search, fresh official-doc fetch) overturned or substantially corrected the original finding. Lesson: when Tony says "that doesn't sound right" or asks a clarifying "why," treat it as a signal to re-verify from source, not just to explain the existing answer more persuasively.

## Validated: testing a real API key live, safely, when authorized

Tony explicitly asked to test his Amazon PA-API credentials without risking account suspension. Approach that worked: exactly one minimal, read-only, properly-signed request (a single `GetItems` call on his own ASIN), no retries, no loops. The result (403 `AssociateNotEligible`) was more informative than guessing from documentation — it proved the credentials were valid and current, correcting an earlier research claim that PA-API 5 was deprecated. Pattern: when a user authorizes testing their own API key and gives an explicit safety constraint, honor it literally (one call, minimal scope) rather than skipping the test out of general caution.

## Browser automation: a fresh session cannot join a user's already-open tab

Tony twice assumed "I have it open in my browser, just look at it" would let the agent see his specific open tab. It can't — `claude-in-chrome`'s session-scoped tab groups are isolated per conversation; a new tab in the same browser/profile shares login cookies but not the actual tab. Workaround that works: open a fresh tab and navigate directly to the target URL — cookies/sessions usually carry over even though the tab doesn't. When they don't (e.g. Amazon required a password despite Redbubble/KDP working via cookies), use `request_credentials`/`autofill_credential` rather than asking Tony to paste a password.
