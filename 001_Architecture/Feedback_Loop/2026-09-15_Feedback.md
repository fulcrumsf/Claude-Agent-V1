# Feedback Loop — 2026-09-15

## Never add metadata/tags/fields Tony didn't ask for, even as a helpful-seeming flag
He rejected `needs-enrichment` outright: "I never approved that tag." Same for the forced `github-repo` tag and `search_for` field — all were process_image_ingest.py additions from before tonight that nobody had signed off on. **Why it matters:** a script silently inventing its own bookkeeping fields/tags erodes trust in what's actually in the vault. **How to apply:** any new tag, flag, or frontmatter field added to an ingest/classification pipeline needs an explicit ask or approval first — don't add "for later" without checking.

## When a UI action visually commits (a chip turns blue, a checkbox checks), it must actually commit
Tony's exact words: "when the tag goes blue, that is me applying it... I don't understand why I need to press Apply and then Ingest." A staged-draft-requiring-a-separate-apply-click pattern doesn't match how a toggle *looks* like it behaves. **How to apply:** in any picker/toggle UI, either make the visual state and the saved state the same thing (apply on every change), or don't use a visual metaphor (color change, checkmark) that implies immediate effect.

## Read ALL of the relevant context sources, not a sample
When asked to read "all my channel MDs" for classification context, an initial pass read only the header block of all 12 docs, then deep-read just 2 of them. Tony's correction: "look through all my folders... don't just select a few to read." **Why it matters:** the two he wasn't deep-read on (Board-Nomad, Polyoculis) turned out to have directly decision-relevant content (Board-Nomad's food/travel pillars created a real Personal-vs-Content_Ideas ambiguity; Polyoculis has a distinctive recognizable visual style). **How to apply:** when told to read a set of context files for a decision, read all of them at the depth needed to actually extract decision-relevant detail — a shallow skim-all-then-deep-dive-a-few pass isn't the same as reading them.

## Test destructive/confirm-gated actions via direct API calls, not by clicking the live UI
A native `confirm()` dialog getting triggered/auto-accepted during agent-driven browser testing is a real, observed risk (see the 84-item wrong-tag ingest incident, [[project_ingest_visualizer]]). **How to apply:** whenever verifying a button that moves/deletes real files, call the underlying endpoint directly with curl/python first — reserve live UI clicks for things with no destructive side effect, or for showing the user rather than for my own verification.

## Lock in a validated ad-hoc process as the standard pipeline, but confirm the exact scope of "locked" first
Tony said "lock this into the pipeline for the shorts, meaning the process that you did should be the locked-in pipeline for shorts... please ask me any questions if you don't understand." Two things were genuinely ambiguous and worth asking rather than assuming: (1) whether the upload should go public immediately or private-first like the long-form review, and (2) whether "Hybrid" becomes a fixed default or the pipeline should still render all three variants (Group/Subject/Hybrid) for comparison every time, since the tool's own README explicitly said Hybrid was "Tony's preference for Part Three specifically, not a global default." **Why it matters:** locking in a process is a standing decision that changes future default behavior — guessing wrong on scope (e.g., silently skipping the variant comparison, or silently going public) would be hard to notice until several videos later. **How to apply:** when told to "lock in" or "make this the default" after an ad-hoc success, identify what specifically was ambiguous about scope (mode choice, visibility/privacy, which channel it applies to) and ask a focused question per ambiguity rather than assuming the most literal reading.
