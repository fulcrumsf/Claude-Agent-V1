# Feedback Loop — 2026-10-15

## "Cite a source" is not the same as "real data" — the source itself must be independent

Escalation of `feedback_real_data_over_opinion_scoring`. Tony's exact words, reviewing the 2026-10-14 scorecard's citation table: "you are sourcing articles... that's not backed by real data." The specific failure: nearly every external citation was vendor/agency content with a conflict of interest (Digistore24's own blog picking its "top 10" products, Pinterest's own ad case study, an Etsy-tool vendor's ROAS claim). A source link isn't evidence just because it has a URL.

**How to apply:** when scoring/ranking, before citing any external claim, ask who benefits from the claim being believed. Vendor/platform/agency content about itself is commentary, not data, even when it cites numbers. Prefer: (1) live API pulls of the user's own accounts, (2) independent/academic/journalistic sources with disclosed methodology, (3) direct observation (scraping a public page for a fact it displays, not a vendor's interpretation of that fact). When Tony pushed further the same day ("using actual API keys... not just a web search"), the real fix was removing ungrounded claims from scoring entirely rather than finding a "better" article — see the scorecard's "Removed from scoring" table.

## Real data on the user's own accounts beats believing an assumption about tool availability

Twice this session, an assumed "no API exists" turned out wrong on direct verification: Composio's dashboard key looked dead but OAuth worked fine; Digistore24 was assumed API-less but has a full REST API + official MCP. **How to apply:** verify "X has no API" claims directly (search their own docs, try to register) before reporting a gap as confirmed — don't let a user's own stated assumption, or an earlier research pass's conclusion, stand in for a fresh check.

## A mechanical block beats a repeated memory promise, for a failure that already recurred

Tony's exact words after a second credential-echo incident: "You keep making these mistakes... that is your fault... You need to put something hard-coded... that blocks you." A memory note (written 2026-10-14) did not prevent a repeat the next day. **Why it matters:** behavioral self-correction via memory is not a safeguard for anything security-relevant that has already failed once — it's a reminder, not a control. **How to apply:** for any repeated safety-relevant failure, the second occurrence should produce an actual mechanical control (a hook, a script, a config change) tested to verify it fires, not another memory entry restating the rule. Built `~/.claude/hooks/redact_secrets.py` this session as the concrete example — see `001_Architecture/Memory` note and Claude's own cross-session memory.
