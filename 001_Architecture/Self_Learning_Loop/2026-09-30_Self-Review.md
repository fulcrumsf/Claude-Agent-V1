# Self-Review — 2026-09-30

## What went well

- **Verifying every subagent build independently, file-by-file, before committing, caught nothing wrong tonight — but it was still the right process, not wasted caution.** Both `/lab-plan` builds (Claude Code, Gemini) came back from their build agents with accurate self-reports, confirmed by independently reading the actual code, running the actual tests, and checking actual committed diffs. The value wasn't catching a lie — it was that the verification itself produced the confidence to commit without reservation, and it would have caught a problem had one existed (per [[feedback_subagent_driven_development]] and the 09-27 incident where a builder's self-report turned out not to be trustworthy).
- **Treating a pasted answer from another AI (Antigravity's assistant) as a claim to verify, not a fact to build on, caught a real dead end before any code was written around it.** One of its three suggested options (`gemini --model -p`) was silently wrong — already disproven minutes earlier in this session. Checking the other two separately (the `BeforeModel` hook, the `google-antigravity` SDK) found one real-but-unusable and one real-and-usable. Had I built on the recommendation wholesale, roughly a third of the eventual implementation effort would have gone toward a dead CLI path.
- **Repeatedly correcting an unsafe design pattern (automatic criticality/stakes judgment by a classifier) the moment it reappeared in a new shape, rather than re-deriving the critique each time.** This came up three separate times tonight (criticality gating for the picker lane, `/lab-build`'s containment model, `/lab-plan`'s scoring mechanism) and each time the same root lesson from the earlier rolled-back frontier-enforcement system applied directly. Recognizing the pattern early kept each design pass shorter than it would have been starting from scratch.

## What was corrected, and should stick

- **Communication style drifted toward technical density several times and had to be pulled back — this is a recurring correction, not a one-off.** Tony corrected this explicitly at least three separate times tonight with near-identical wording ("too many technical terms," "seventh grader," "if it works, I don't care to hear about it"). The pattern: a long, careful technical build deserves a short, plain-language status summary, not a condensed version of the same technical summary. Next session: default to this register from the start on status updates, not as a correction to react to.
- **A design recommendation (the `.claude/worktrees/` folder location) violated an already-stated hard rule of Tony's (cross-harness visibility) and wasn't checked against that rule before being proposed.** The rule had been stated earlier in a different context; it should have been checked against every subsequent folder-location decision, not just applied retroactively after Tony caught it. Going forward: when a workspace rule has been stated once, treat it as a standing checklist item for every structurally similar decision afterward, not something to recall only when directly relevant.
- **Assumed Antigravity and the standalone `gemini` CLI shared one login, and built an initial assumption on it, before checking.** Tony's own question ("are you trying to log in through the terminal or via Antigravity? what are you trying to do?") was the thing that triggered the actual check, not an internal catch. The two products turned out to have completely separate credential stores. Lesson: when two tools sound related by name or vendor, confirm they're the same underlying system before treating a test of one as informative about the other.

## Recurring pattern worth naming

Three times tonight, a locked design got revisited and meaningfully improved after Tony pushed back with a concrete objection grounded in how he actually works (cost of dual-run, the nature of generated-media pipelines needing real API calls, wanting all harnesses immediately). Each time, the right move was a full honest reconciliation pass (dispatched to opus-deep with the real objection as the explicit brief), not a quick patch defending the prior design. This workspace's iterative-design style rewards treating user pushback as a signal the design is still wrong in a specific, nameable way — not as a nitpick to smooth over.
