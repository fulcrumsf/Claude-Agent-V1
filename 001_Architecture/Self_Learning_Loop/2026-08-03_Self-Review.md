## What went well

- **Ship-then-critique beat plan-then-critique.** Running the full real production before asking Tony for more feedback surfaced two concrete, high-leverage caption fixes in two fast rounds (content, then position, then a follow-up on timing) that would have been hard to anticipate from the style guide alone. The whole loop — generate, critique, fix, re-render, re-approve — took minutes per round because the pipeline's individual stages (image gen, video gen, assembly, text overlay) were already built, tested, and composable from prior SDD plans. This validates building the pipeline stage-by-stage with real tests before ever running a full end-to-end production.
- **Verifying before claiming done.** Pulled actual frames (ffprobe + ffmpeg frame extraction + Read/vision) at every render stage instead of trusting exit codes. Caught the frame-0 fade-in issue would have required Tony to catch it live if I'd only checked duration/codec.
- **Caught graphify's cost gate before spending tokens on 979 files of binary media.** The skill's own size gate did its job — I stopped, asked, and the resulting scoping conversation ("graphify should never process video or images") produced a durable, repo-wide policy fix instead of a one-off workaround.

## What went wrong / what to watch

- **Wasted one full detect+build cycle on a documentation bug.** I trusted REGISTRY.md's claim that `.graphify/.graphifyignore` was the ignore-file location, edited it, and only discovered it wasn't actually read by the tool after re-running detection and seeing zero effect. Should have checked the tool's actual source (`grep -rn graphifyignore` on the installed package) before trusting the doc the first time — a 30-second check that would have saved a full detect cycle. **Lesson: for tool configuration that doesn't visibly confirm itself (an ignore file with no immediate feedback), verify against the tool's source before trusting internal docs, even when the docs look authoritative.**
- **Subagents produced 6 semantic-extraction nodes/edges with directory paths as `source_file` instead of actual files** (e.g., a node representing "the Anomalous Wild channel" pointed at the channel's root folder, not a specific file). This crashed `save_semantic_cache` on `read_bytes()`. Not caught until the cache-save step failed. **Lesson: when dispatching parallel extraction subagents, a validation pass on `source_file` (must be an existing file, not a directory) before attempting to cache would catch this before the failure, not after.**
- **Manual community labeling was a real time cost** at 117 communities from a single-domain build — hand-labeled ~25 substantive ones and auto-derived the rest from each community's dominant node label. Reasonable trade-off given effort constraints, but worth knowing this scales poorly for larger domains; a smarter default (e.g., only hand-label communities above a size threshold, which is roughly what happened organically here) could be made an explicit rule rather than an improvised choice.

## Recurring pattern to keep watching

- This is now the **third and fourth time** a stale/incorrect internal doc caused wasted work (previously: kie-cli status-string vocabulary mismatches in image/music generation; now: the `.graphifyignore` location). The common thread: docs describing *how a third-party or installed tool behaves* go stale faster than docs describing *this repo's own code*. Worth remembering to verify tool behavior against the tool's actual source/help output before trusting a workspace doc's claim about it, specifically for external tools (kie-cli, wavespeed, graphify) — not needed for docs about code we wrote ourselves, which stay accurate by construction as long as they're updated alongside the code.
